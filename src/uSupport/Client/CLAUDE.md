# uSupport backoffice frontend

TypeScript + Lit on `@umbraco-cms/backoffice` ~17.5. Vite builds `src/index.ts` as one ES module to `../wwwroot/uSupport.js` (served at `/App_Plugins/uSupport/uSupport.js`); `@umbraco/*` imports stay external. `public/umbraco-package.json` registers that file as a `backofficeEntryPoint`.

Commands: `npm run build` (tsc + vite), `npm run watch`, `npm run generate` (API client, needs the demo site on https://localhost:44311).

## Startup

`src/index.ts` registers every manifest from `src/manifests.ts`, then configures the generated API client with the backoffice auth token (`UMB_AUTH_CONTEXT`). Nothing else should call `client.setConfig`.

## Layout

```
src/
  index.ts, manifests.ts        entry point; manifests.ts aggregates each folder's manifest.ts
  constants.ts                  section/menu/workspace aliases, entity types, workspacePath(), markupOf()
  api/                          GENERATED by @hey-api/openapi-ts. Never edit by hand; regenerate and commit
  repository/usupport.repository.ts   the only place that calls api/. Re-exports models as Ticket, TicketType, ...
  section/                      uSupport section, sidebar menu, Tickets + Settings menu items
  dashboards/                   admin dashboard (uSupport section) and user dashboard (Content section)
  tickets/                      tickets overview workspace, single-ticket routable workspace (Ticket + History views),
                                create/open ticket modals, delete action, shared components (table, comments, property)
  ticket-types/, ticket-statuses/   thin configs over shared/lookup*; each has an editor element + workspace context
  shared/                       generic "lookup" machinery (tree, overview, create/sort/delete actions, sort modal), display helpers
  settings/                     settings workspace view
  localization/                 en.ts, ja.ts
```

## Patterns to follow

- **Data access**: `new USupportRepository(this)` from any element or controller. Methods return `data` or `undefined` on error (errors already surface as backoffice notifications via `tryExecute`); deletes return a boolean. New endpoint: regenerate `api/`, add one method to the repository, use the re-exported type name.
- **Types and statuses are one feature**: `shared/lookup.ts` `LOOKUPS` describes the differences, `shared/lookup.manifests.ts` generates the tree, menu item, root overview workspace, item workspace and create/sort/delete entity actions. Change behaviour for both in `shared/`, not in two places.
- **Workspaces**: routable workspace contexts extend `UmbContextBase`, provide `UMB_WORKSPACE_CONTEXT`, route `edit/:id` (and `create` for lookups), hold state in `UmbObjectState`, and set an `UmbEntityContext` so entity actions appear in the workspace menu. See `tickets/workspace/ticket-workspace.context.ts`.
- **Extensibility**: other packages can add tabs to a ticket via a `workspaceView` conditioned on `uSupport.Workspace.Ticket`. Keep aliases in `constants.ts` stable.
- **Ticket type custom property**: `tickets/components/ticket-property.element.ts` loads the admin-chosen data type by key and renders its property editor UI. The value is stored as a JSON string (same as v13); unparseable v13 values are shown as stored.
- **Rich text**: summaries and comments use Umbraco's built-in Richtext editor data type (`USUPPORT_RICH_TEXT_DATA_TYPE_KEY`); `markupOf()` extracts the HTML from the stored value.
- **Navigation**: build links with `workspacePath(entityType, path)`.
- **Localization**: no hard-coded UI text. Use `#uSupport_*` keys in manifests and `this.localize.term(...)` in elements; add every key to both `en.ts` and `ja.ts`.
- **UI**: use UUI / `umb-*` components and the backoffice look; match existing elements rather than adding styles.
- Manifest aliases use the `uSupport.<Area>.<Thing>` form; element tags use `usupport-*`.

## E2E

`src/uSupport.E2E` (Playwright + `@umbraco-cms/acceptance-test-helpers`) runs `admin` and `editor` projects against the demo site. Test ids use the `data-mark` attribute. Shared fixtures and URLs are in `tests/helpers.ts`. When you change a flow covered there (create ticket/type/status), run or update those specs.
